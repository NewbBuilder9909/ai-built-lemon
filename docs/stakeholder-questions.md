# Stakeholder questions and feature gaps

Working hypotheses for a services organisation. These are questions to validate with real professionals, not a claim that every organisation uses the same workflow. The priority is the decision and evidence needed, followed by the feature. This follows the [GOV.UK service standard](https://www.gov.uk/service-manual/service-standard/point-1-understand-user-needs) and [user research guidance](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs): understand the whole task and test assumptions with likely users. [Regular service testing](https://www.gov.uk/service-manual/technology/quality-assurance-testing-your-service-regularly) informs the build checks below.

Legend: **Live** = visible in the application; **Partial** = some evidence exists but the answer is incomplete; **Missing** = proposed feature. Every answer needs an as-of date, data coverage and a route to its source evidence.

## Test shape required for each question

Each question should gain three deterministic cases when its feature is implemented: **positive** (adequate evidence and a correct answer), **negative** (an adverse business condition prompts action), and **unknown** (missing, stale or ambiguous evidence blocks a confident answer). Add tenant and access tests wherever a question crosses a customer or permission boundary. A build must fail when an implemented answer changes numerically or loses its uncertainty/coverage signal. Human task testing checks whether the professional can understand and act on that answer; arithmetic tests alone cannot establish that.

The current first slice is estimate coverage beside workstream variance. It makes the PMO question more honest but does not classify the whole report as reliable. Next implementation slices should be the quality ledger and dated capacity reconciliation, since those support several roles and expose incorrect healthy-looking outputs.
